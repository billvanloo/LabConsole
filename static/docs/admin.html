ADMIN GUIDE

SETUP, CONFIGURATION, AND CARE OF THE CONSOLE

01 PRINTER PREREQUISITES

The console reaches every printer over the local network, and a printer can be set up for it in either of two modes. Pick one per printer:

MODEWHAT YOU GETWHAT YOU GIVE UP
Cloud mode (printer stays on Bambu Cloud) Status, progress, ERROR detection, temperatures, AMS, and the camera. Bambu Studio and Bambu Handy keep printing and monitoring over the cloud as before. Some controls may be refused. Firmware with Bambu’s 2025 authorization change rejects certain commands from third-party software while the printer is cloud-connected; a refused command simply has no effect.
LAN Only + Developer Mode Everything, including pause, resume, stop, light, and starting prints. The printer cannot connect to Bambu Cloud: no Bambu Handy, and Bambu Studio can only reach it from the same local network.

Cloud mode is the usual choice in a shared lab where people send prints from their own computers. Verified on an X1C: status, the live camera, and the chamber light all work in cloud mode. Pause, resume, stop, and start print have not been verified there yet, so test them on your own printers before relying on them.

Then, on each printer:

  1. Update to recent firmware.
  2. LAN Only + Developer Mode only: switch to LAN Only Mode and enable Developer Mode (Settings → General/Network). Skip this step for cloud mode.
  3. Record the Access Code (Settings → Network) and Serial Number (Settings → Device).
  4. X1-series / H2D only: enable LAN Mode Liveview so the RTSPS camera stream is available. This setting works in both modes.
  5. Optional: a fixed address per printer. Discovery recognizes each printer by its serial number and follows it when DHCP hands it a new address, so fixed addresses aren’t required, and the console has run this way on a school network. Putting each printer’s current address in config.json as ip is still worth doing: a correct address connects instantly, and a stale one is corrected by discovery within a few seconds. Ask your network administrator for DHCP reservations only if discovery can’t see the printers. Signs of that are a SSDP listener … unavailable warning in the log, or a panel that stays OFFLINE after its printer gets a new address.
◈ NETWORK REQUIREMENT

The console host must be able to open connections to each printer. Wi-Fi networks with client isolation (common on school and guest networks) block this, and every panel stays OFFLINE in either mode. To check a network before installing, run a quick port test from a laptop on the same network: ports 8883 (status) and 322 (X1/H2D camera) or 6000 (A1/P1 camera) must answer.

◈ FIRMWARE UPDATES

In cloud mode, which controls work depends on the printer’s firmware. If controls work today, a later firmware update may restrict them. Monitoring and the camera are not affected.

◈ NOTE

Regenerating a printer’s access code invalidates the one in config.json — the panel will go OFFLINE until the config is updated.

02 INSTALLATION

sudo apt update && sudo apt upgrade -y
sudo apt install -y git python3-venv ffmpeg
#   (ffmpeg is only needed for X1/H2D cameras)
git clone https://github.com/billvanloo/LabConsole.git /home/pi/lab-console
cd /home/pi/lab-console
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp config.example.json config.json
nano config.json              # fill in serials + access codes
.venv/bin/python server.py    # open http://<pi-address>:8080

To evaluate without printers, run .venv/bin/python server.py --demo — no config file is required.

◈ WHY A VIRTUAL ENVIRONMENT

Current Raspberry Pi OS (Bookworm and later) and Ubuntu 23.04+ refuse a plain pip3 install with error: externally-managed-environment, to keep pip from overwriting packages the OS depends on. The .venv folder holds the console’s own copies of its libraries instead. Always start the console with .venv/bin/python — plain python3 won’t see those libraries. The systemd unit already does this.

◈ NOTE

The paths above and in lab-console.service assume the user pi. Newer Raspberry Pi OS images have no default pi account — if you chose a different username, substitute it for pi in /home/pi/lab-console here and in the service file’s User=, WorkingDirectory= and ExecStart= lines.

RUNNING ON UBUNTU / OTHER LINUX HOSTS

The console runs unchanged on a standard Ubuntu machine (desktop or server) instead of a Raspberry Pi — nothing in the code is Pi-specific. Install the same way:

sudo apt update && sudo apt upgrade -y
sudo apt install -y git python3-venv ffmpeg
git clone https://github.com/billvanloo/LabConsole.git ~/lab-console
cd ~/lab-console
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

A few environment differences to check:

  • Firewall — Ubuntu often runs ufw, which Raspberry Pi OS does not enable by default. Allow the console’s port: sudo ufw allow 8080/tcp.
  • Same LAN as the printers — SSDP discovery is a passive listener; the host must sit on the same network segment as the printers, not behind a router hop or separate VLAN.
  • Laptops — Wi-Fi power-saving can drop the idle discovery socket or let the machine sleep. Disable suspend and Wi-Fi power management, or use a wired/always-on machine.
◈ NOTE

A typical Ubuntu machine has far more headroom than a Pi 3 — camera.max_streams in the config can safely be raised above 1 if you want multiple live camera views at once.

log_levelINFODEBUG adds unreadable reports, discovery noise, and messages answering other apps; WARNING keeps only problems.

LOG FILE

The console writes what it does and what goes wrong to lab-console.log in its folder (tail -f lab-console.log to watch it live). Access codes are masked as ****. Every command sent from the console is logged with the printer’s answer: printer accepted, printer REJECTED, or, when the printer stays silent for 10 seconds, no reply. That last one is what a command quietly refused by cloud-mode firmware looks like. Also logged: MQTT connections and refused logins (a wrong access code), each change of printer state with HMS codes in the format Bambu’s wiki uses (e.g. 0300_0100_0001_0007), file list and upload failures, camera failures, and discovery problems.

04 RUN AT BOOT / KIOSK DISPLAY

sudo cp lab-console.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now lab-console
# logs:
journalctl -u lab-console -f

For a dedicated wall display, point a kiosk browser at the console, e.g. chromium-browser --kiosk http://localhost:8080. The frontend pauses its panel cycling while the browser tab is hidden, so an always-on display costs the Pi almost nothing when nobody is looking at it.

05 TROUBLESHOOTING

SYMPTOMLIKELY CAUSE / FIX
Anything not working as expectedStart with lab-console.log in the console folder (section 03). It records each command with the printer’s reply, and each connection, camera, and file error.
Panel OFFLINEPrinter unreachable over MQTT. Check power, LAN, that the access code matches, and (for LAN Only printers) Developer Mode. If IPs changed, discovery re-finds printers within a minute of their next announcement. If every panel is OFFLINE, the network may isolate Wi-Fi clients — see the network requirement in section 01.
Pause / stop / light has no effectCheck the log for that command. no reply or printer REJECTED means the printer is in cloud mode and its firmware refuses that command from third-party software. Use the printer screen, Bambu Studio, or Bambu Handy, or switch that printer to LAN Only + Developer Mode.
X1/H2D camera NO SIGNALLAN Mode Liveview disabled, or ffmpeg not installed. Some H2D firmware versions have temporarily shipped without local liveview pending updates — status and control keep working.
Camera face stays blackThe console log gives the reason on lines starting [camera …] (lab-console.log, journalctl -u lab-console -f, or the terminal running server.py). certificate verify failed comes from a console copy older than the fix that accepts the printer’s self-signed certificate, run with a newer ffmpeg. Update the console.
A1 camera is ~1 fpsThat is the chamber camera’s hardware rate, not a fault.
Start print: file not foundSwitch sdcard_url_base to file:///mnt/sdcard/.
SD list emptyOnly files in the SD card root are listed; uploads also go to the root.
pip3 install fails: externally-managed-environmentThe OS blocks system-wide pip installs. Create the virtual environment and install into it: python3 -m venv .venv, then .venv/bin/pip install -r requirements.txt. If venv is missing, sudo apt install python3-venv.
ModuleNotFoundError: aiohttpStarted with plain python3 instead of .venv/bin/python.
LINK red in the status barBrowser lost its WebSocket to the Pi; it reconnects automatically. If persistent, check the service with journalctl.
▲ SECURITY

The console has no login and printer access codes live in config.json. Keep it on a trusted LAN/VLAN and don’t expose port 8080 to the internet.
